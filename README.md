# Notify — черновик архитектуры

Модель находится в папке `architecture/`: типы элементов — в `specification.c4`, элементы и связи — в `model/`, представления — в `views/`. Это предварительная логическая схема, а не описание уже работающей системы или схема развёртывания.

## Посмотреть схемы

Установите Node.js и запустите в этой папке:

```sh
npx likec4@1.60.0 start
```

Откройте адрес, который покажет команда (обычно http://localhost:5173). Для проверки модели можно запустить `npx likec4@1.60.0 validate`.

Доступны контекст Notify и автоматически создаваемый общий вид. Для редактирования можно открыть папку проекта в VS Code с расширением LikeC4. В [LikeC4 Playground](https://playground.likec4.dev/) нужно загрузить все файлы `.c4` из `architecture/`: LikeC4 объединяет их в одну модель.

## Допущения

- REST и Kafka — альтернативные точки входа. Kafka на схеме также используется для внутренних заданий; физическая топология и границы брокеров не определены.
- Компоненты Notify показаны по ролям; число процессов, виртуальных машин и способ их развёртывания ещё не выбраны.
- PostgreSQL — основное хранилище, Redis — для кэша и лимитов, ClickHouse — для аналитики. Состав данных и способ передачи в аналитику требуют проработки.
- Компоненты телеметрии показаны концептуально; конкретный стек и место хранения логов и метрик не выбраны.
- Модель мультиарендности, изоляция, контракты API, гарантии доставки, обработка результатов провайдеров и механизмы повторов ещё не согласованы.

## Согласованные решения о доставке

- Рассылка создаётся до отправки; аудитория загружается порциями, затем вызывающий сервис запускает её. После запуска новые порции не принимаются.
- История уведомлений записывается асинхронно только после успешной отправки провайдеру. Предварительные статусы сообщения: `sent`, `delivered`, `read`; до успешной отправки отдельная запись уведомления не создаётся.
- `deadline_at` необязателен при запуске рассылки и в индивидуальной Kafka-команде. Отмена записывается в `cancelled_at`. Воркер проверяет их до отправки и пропускает просроченные или отменённые задания с причиной для прогресса и аналитики. Уже принятые провайдером сообщения не отзываются; TODO: согласовать распространение отмены через Redis и границу гонки с отправкой.
- Для индивидуальной Kafka-команды задаётся тип `sms`, `push` или `email`; Notify выбирает канал. Каждый канал использует одного провайдера, один провайдер может обслуживать несколько каналов. TODO: определить правила выбора канала.
- Пользователи первоначально загружаются однократно из внешних систем, затем обновляются через Kafka. При отсутствии пользователя или адреса соответствующая отправка завершается ошибкой. TODO: согласовать границу начальной загрузки и потока событий.
- Аудитория может содержать `user_id`, `phone`, `email` или `push_token`; тип задаётся в `recipient_type`, значения — в `recipients`.
- На границе PostgreSQL и Kafka запуск защищается `run_id` fencing и восстановлением, а не общей транзакцией. Вызов провайдера и фиксация результата не атомарны: после сбоя допустима повторная отправка.
