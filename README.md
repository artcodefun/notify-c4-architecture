# Notify — черновик архитектуры

Модель находится в папке `architecture/`: типы элементов — в `specification.c4`, элементы и связи — в `model/`, представления — в `views/`. Это предварительная логическая схема, а не описание уже работающей системы или схема развёртывания.

## Посмотреть схемы

Установите Node.js и запустите в этой папке:

```sh
npx likec4@1.60.0 start
```

Откройте адрес, который покажет команда (обычно http://localhost:5173). Для проверки модели можно запустить `npx likec4@1.60.0 validate`.

Доступны контекст Notify и автоматически создаваемый общий вид. Для редактирования можно открыть папку проекта в VS Code с расширением LikeC4. В [LikeC4 Playground](https://playground.likec4.dev/) нужно загрузить все файлы `.c4` из `architecture/`: LikeC4 объединяет их в одну модель.

## Допущения

- REST и Kafka — альтернативные точки входа. Kafka на схеме также используется для внутренних заданий; физическая топология и границы брокеров не определены.
- Компоненты Notify показаны по ролям; число процессов, виртуальных машин и способ их развёртывания ещё не выбраны.
- PostgreSQL — основное хранилище, Redis — для кэша и лимитов, ClickHouse — для аналитики. Состав данных и способ передачи в аналитику требуют проработки.
- Компоненты телеметрии показаны концептуально; конкретный стек и место хранения логов и метрик не выбраны.
- Модель мультиоператорности, изоляция, контракты API, гарантии доставки, обработка результатов провайдеров и механизмы повторов ещё не согласованы.

## Согласованные решения о доставке

- Рассылка создаётся до отправки; аудитория загружается порциями, затем вызывающий сервис запускает её. После запуска новые порции не принимаются.
- Payload уведомления един для всех каналов: `title`, `body`, `image_url`, `data`. Адаптер выбранного канала использует только поддерживаемые поля; канал-специфичные расширения не предусмотрены.
- Кампания задаёт ровно один из прямого payload или шаблона. Шаблон фиксируется в конкретной версии при создании кампании и может содержать простые плейсхолдеры `{name}`; данные для них передаются для каждого адресата в template.recipient_data.
- Delivery и retry-воркеры напрямую сохраняют в PostgreSQL delivery_status сообщения: `pending`, `success`, `fail` или `canceled`, а также `retry_count`. Отдельный receive_status (`sent`, `delivered`, `read`) фиксирует получение сообщения и после успешной отправки начинается с `sent`. Отдельная таблица попыток доставки не используется. Каждое изменение публикуется в Kafka для загрузки в ClickHouse.
- `deadline_at` необязателен при запуске рассылки и в Kafka-запросе inline-рассылки. Отмена записывается в `cancelled_at`. Воркер проверяет их до отправки и пропускает просроченные или отменённые задания с причиной для прогресса и аналитики. Уже принятые провайдером сообщения не отзываются; TODO: согласовать распространение отмены через Redis и границу гонки с отправкой.
- Kafka-запрос создаёт inline-рассылку. `campaign_id` — необязательный UUID вызывающего сервиса: он нужен для отслеживания изменений рассылки и делает повтор запроса идемпотентным; без него Notify создаёт внутренний идентификатор. Для запроса задаются тип `sms`, `push` или `email`, `recipient_type` и необязательный `channel_key`: при наличии ключа используется указанный канал, иначе Notify выбирает самый дешёвый подходящий канал данного типа. Каждый канал использует одного провайдера, один провайдер может обслуживать несколько каналов. TODO: определить расчёт стоимости и поведение при отсутствии подходящего канала.
- После запуска потребления событий Kafka существующие пользователи однократно загружаются SQL-скриптом из других баз данных. При отсутствии пользователя или адреса соответствующая отправка завершается ошибкой.
- Аудитория может содержать `user_id`, `phone`, `email` или `push_token`; тип задаётся в `recipient_type`, значения — в непустом `recipients`. Отдельный механизм массовой рассылки всем пользователям ещё предстоит определить.
- Отсутствие пользовательской настройки означает разрешённую доставку. UserDeliveryOptOut явно отключает SMS или email либо push для конкретного мобильного приложения; delivery и retry-воркеры проверяют opt-out перед каждой попыткой.
- На границе PostgreSQL и Kafka запуск защищается `run_id` fencing и восстановлением, а не общей транзакцией. Вызов провайдера и фиксация результата не атомарны: после сбоя допустима повторная отправка.
